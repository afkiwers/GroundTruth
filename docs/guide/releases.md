# Releases (maintainers)

How a GitHub release builds, signs and publishes the packages. Back to the [README](../../README.md).

**Releases.** Publishing a GitHub release runs `.github/workflows/release.yml`: it builds what `build_package.cmd` builds (the KiCad package and the compute-server package of the same version, the server package signed with the release key), attaches both and the signature to the release, and publishes the repository above on GitHub Pages with every release's version (`tools/make_pcm_repository.py`). The release's tag is the plugin's version, in the build numbering every package has: pyproject's major.minor and a counter that grows every 10 minutes (`0.1.42600`). Tag the release with a build number: `python tools/make_pcm_package.py --print-version` prints the current one (`build_package.cmd` shows the number of the package it builds). The workflow builds the packages with exactly that version (the packages, `version.txt` and the KiCad repository carry it); a tag of another form, or another major.minor than pyproject's, stops the build. KiCad offers a release as an update when its number is higher than the one installed, so a release tagged with the current build number is newer than every earlier build. A pre-release is listed as `testing`, a release as `stable`. The private release key is never in the repository: the workflow takes it from an encrypted Actions secret, writes it to an owner-only temporary file for the build and deletes it; it checks the key against `tools/release_key.pub` (the public half the servers trust) and fails rather than sign with another key, and it checks the repository and the built packages for a private key before uploading. One-time setup on github.com:

1. **Settings → Secrets and variables → Actions → New repository secret**: name `GROUNDTRUTH_RELEASE_KEY`, value the whole content of `%LOCALAPPDATA%\GroundTruth\release\release_ed25519.pem` (with its BEGIN / END lines). Or, with the GitHub CLI logged in: `gh secret set GROUNDTRUTH_RELEASE_KEY --repo afkiwers/GroundTruth < "%LOCALAPPDATA%\GroundTruth\release\release_ed25519.pem"`.
2. **Settings → Pages → Build and deployment → Source: GitHub Actions**.
3. **Settings → Environments → github-pages → Deployment branches and tags**: add a tag rule `*.*.*` (a release runs from its tag, e.g. `0.1.1`; by default only `main` may deploy).

A release made before the setup (or one to build again): **Actions → Release packages → Run workflow** with its tag.

**KiCad's official repository.** To list GroundTruth in the Plugin and Content Manager without adding a repository URL, the package goes to KiCad's metadata repository by a merge request ([gitlab.com/kicad/addons/metadata](https://gitlab.com/kicad/addons/metadata), rules at [dev-docs.kicad.org/en/addons](https://dev-docs.kicad.org/en/addons/)). The files it needs are `packages/io.github.afkiwers.groundtruth/metadata.json` (the package with every release's version: download URL, SHA-256, sizes) and `icon.png`. Each release's workflow publishes them on GitHub Pages under `kicad-metadata/packages/io.github.afkiwers.groundtruth/`; by hand, from the releases' `*.pcm.json` files in a folder: `python tools/make_pcm_repository.py kicad-metadata ENTRIES_DIR PACKAGE.zip OUT_DIR`. The first time: fork the metadata repository on GitLab, copy the folder into `packages/` on a new branch, push, wait for the fork's `validate` and `build` pipeline (its log links a temporary repository to try in KiCad), then open the merge request. For each later release: replace `metadata.json` with the new one (earlier versions keep their download fields unchanged; a stable version may only become deprecated) and open another merge request.
